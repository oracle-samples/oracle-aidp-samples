# Night Shift agent for Oracle AI Data Platform

An agent that takes the data team's night shift. It runs as an ordinary scheduled Workflow job on Oracle AI Data Platform (AIDP), and before it asks anyone for anything it proves its work: every repair it proposes is replayed under realistic delivery faults on a shallow clone of the real table. A person approves in a Workbench notebook under their own identity; the next tick writes the approved repair as a runbook row. The agent never edits anyone's job.

Pure Python plus Spark SQL on Delta tables. No external services beyond the platform's own `ai_generate` model function. The unit tests run locally with pandas and duckdb and never call the platform.

## What a tick does

Every 30 minutes the job `nightshift_heartbeat` runs on a cluster and:

1. **Evidence.** Records flight-recorder rows from this cluster's own Spark UI (stage and SQL evidence) and counts the wake events waiting for the external actuator. Error-text fingerprinting into a small label vocabulary (`TIMEOUT`, `PERMISSION_DENIED`, `SCHEMA_MISMATCH`, `EXTERNAL_SYSTEM_ERROR`, ...) and incident upserts (twelve identical failures become one `incidents` row) live in `nightshift/fingerprint.py` and are driven by the optional laptop scripts `scripts/ingest_failures.py` and `scripts/record_incident.py`, which need a workspace client (see below); the in-cluster job cannot read job runs.
2. **Gate.** Every action passes a policy engine. The rules are `Rule` rows defined in code (`nightshift/gate.py::default_rules`) and reviewed like code; the `policy_rules` table the DDL creates is reserved and nothing reads it. Lowest priority first, first deny wins, quarantine to an `approvals` row, rate limits counted from the changes the ledger shows as applied (a dry run spends none). The gate fails closed: an action kind it does not know is denied, a cluster whose run count is unknown is neither stopped nor resized, and nothing runs when the decision row cannot be written. A compute-budget tier (`high`, `normal`, `low_compute`, `critical`, `paused`) decides how much the agent may do; the hysteresis and grace logic in `tiers.py` is fully exercised by the external actuator, while the scheduled job keeps the previous tick's tier unless the ledger has no tick yet.
3. **Replay.** For each watched production statement (one plain `MERGE INTO <table> USING <table>`; anything else is recorded as `rejected`) it builds a shallow-clone sandbox, runs the statement twice, then under five delivery hazards: late, duplicate, out-of-order and retried batches, and revision. Revision delivers a batch of corrections (same key, later timestamp, every other column changed) and then the superseded rows of the same keys once more. The result is diffed against a batch recompute. Verdicts: `replay_safe`, `silent_wrong` (passes a single run, fails run-twice or a hazard), `snapshot_wrong`, `insufficient_coverage`, `crash`. The corrections separate an upsert from an insert-if-absent MERGE; the stale rows after them separate an upsert with an ordering guard from one that lets the last delivery win. A statement that passes while a check exercised no row (a table too small to move, repeat or revise anything) is `insufficient_coverage`, never `replay_safe`, and the verdict lists the checks that had nothing to act on.
4. **Draft.** When a statement grades `silent_wrong`, the job asks the platform's `ai_generate` for one replacement statement and treats the reply as untrusted text: the platform parser must accept it, the declared target and source must match, the target must be a Delta table. The draft is then replayed under the same hazards on a fresh shallow clone of the same table. Only a `replay_safe` draft becomes a `statement_repair` action, and the gate always quarantines it to a person. Cap: three model replies per statement in any 24 h window (a call that fails before a reply does not count but backs the runner off for an hour); a statement with a live `replay_safe` draft is not drafted again; a draft text a person already decided on is never re-proposed. One runner drafts for a statement at a time (a lease row), and the counts are read again once the lease is held. Every model call of a run is made before its first replay.
5. **Ledger.** Everything is a Delta table in `nightshift_ops`: `wake_events`, `ticks`, `budget_ledger`, `llm_ledger`, `policy_rules`, `policy_decisions`, `approvals`, `incidents`, `runbooks`, `actions`, `flight_recorder`, `replay_verdicts`, `repair_drafts`, and more (`charter_history` and `agent_registry` are created by the DDL for the actuator). No hidden state; every screen is a query.
6. **Drain.** Approvals a reviewer recorded in the Workbench notebook are checked, then re-evaluated through the same gate (the recorded approval lifts the quarantine; the draft's verdict must still be fresh). The decision row is written first, the row is claimed (`approved` to `executing`, so two drainers never act on the same row), then the draft lands as a `runbooks` row with who approved it and when, and the approval is marked `executed`. An approved row is only data in a table, so before the gate runs: its kind must be one a quarantine rule can hold; it must be the row the gate opened (the only row with its id, naming a quarantine decision for that exact action from the last 48 hours that no other approval row names); the approver must not be empty or a service identity, and must be on `NS_APPROVERS` when that list is set. A row that fails the first two is marked `failed`; the others stay approved with `DENIED_ON_EXECUTE`.

## Layout

```
night-shift-agent/
  nightshift/            the package (no secrets, no instance identifiers)
    config.py              environment (NS_*) and constants
    tiers.py               budget -> tier, hysteresis, grace
    gate.py                PolicyEngine: rules as Rule rows (hardcoded defaults), first deny wins, quarantine, fail-closed audit, rate limits
    fingerprint.py         error text -> label vocabulary (+ ai_generate SQL for the fallback)
    ledger.py              DDL for the ops tables + SQL builders (idempotent INSERT/MERGE strings)
    recorder.py            flight-recorder cell source (Spark UI REST inside the kernel)
    replay.py              hazard batches, run-twice, diff, grader (pandas/duckdb locally, Spark SQL live)
    merge_adapt.py         a real MERGE -> harness template (target/source placeholders, key columns, ordering guard)
    watch.py               trust boundary for watched statements and model drafts (parser-tree allowlist)
    draft.py               prompt, ai_generate SQL, reply extraction, statement_repair action params
    drain.py               the approval drain the heartbeat runs every tick
    actuator.py            the optional external tick for control-plane actions (dry-run by default)
    aidp_io.py             thin wrapper over a workspace client (lazy import; only the laptop scripts need it)
  jobs/nightshift_heartbeat.py   the scheduled in-cluster task
  jobs/watched_merges.json       the watch list: statements to grade (and whether this runner may draft for them)
  sql/ddl_ops.sql                the ledger DDL as plain Spark SQL
  notebooks/NightShift_Approvals.ipynb   the reviewer's notebook (pending, evidence, draft text, decide, after the tick)
  notebooks/*.py                 cells to paste: flight recorder, replay template, a synthetic failing job
  scripts/                       optional laptop tooling (see below)
  tests/                         pytest, local only
```

## Prerequisites

- An Oracle AI Data Platform workspace with a cluster (Spark 3.5, Delta) and the Workflows feature.
- A catalog where the job may create the schema `nightshift_ops` and create/drop per-run sandbox schemas named `<NS_SBX>_<tick>_<minute>` (default prefix `default.nightshift_sbx`).
- For drafting: `ai_generate` with the model ids named in `NS_DRAFT_MODEL` and `NS_DRAFT_MODEL_LOW` (defaults `xai.grok-4.7` and `xai.grok-4.20-non-reasoning`); set them to the `modelName` values that `SHOW MODELS` lists on your instance. `SHOW MODELS` returns `modelId`, `modelName` and `modelVersion`; `ai_generate` takes the name, and the `modelId` OCID fails with `No model found for name`. `openai.*` names are refused by the draft step on purpose.
- Python 3.12+ for the local tests: `pip install -r requirements.txt`.

## Setup (platform side, no laptop tooling needed)

1. **Upload the agent.** In the Workbench, create `Shared/nightshift/` and upload `jobs/nightshift_heartbeat.py` and `jobs/watched_merges.json` into it, and the `nightshift/` package folder into `Shared/nightshift/pkg/` (the heartbeat adds `/Workspace/Shared/nightshift/pkg` to its import path; `NS_PKG` overrides it). **Then restrict write access on that folder to the job's owner** (see "Security model" below): the scheduled job runs whatever code is in it. To keep the agent out of `Shared/` altogether, upload to a folder only the owner can write and point the job's task path, `NS_PKG` and `NS_WATCHED` at it.
2. **Create the ledger.** In a Python cell of a notebook on the cluster:

   ```python
   import sys
   sys.path.insert(0, "/Workspace/Shared/nightshift/pkg")
   from nightshift.ledger import ddl_statements
   for statement in ddl_statements("default.nightshift_ops"):
       spark.sql(statement)
   ```

   `sql/ddl_ops.sql` holds the same statements as plain Spark SQL, one per `;`. The ledger lives in `default.nightshift_ops`; to use another catalog or schema, pass it to `ddl_statements`, set `NS_OPS` on the job and regenerate the file with `python -m nightshift.ledger <catalog.schema>`. The laptop alternative is `python scripts/deploy_ops_schema.py --apply`, which creates the schema `NS_OPS` names in `.env`.
3. **Describe what to watch.** Edit `Shared/nightshift/watched_merges.json`: one entry per production statement with the target table, its ordering column (`ts`), the source table and the statement text. `"draft": true` lets this runner draft for that statement; start with `false` and turn it on once the verdicts look right. An entry may also name the key columns (`key`); without it the MERGE's ON columns are used. `draft` defaults to true when the key is absent. The file ships with two synthetic entries over `default.nightshift_demo.orders_bronze` / `orders_silver`, built by `notebooks/synthetic_failing_job.py` (or `scripts/run_synthetic.py` from a laptop): an insert-if-absent MERGE that grades `silent_wrong` on the revision hazard and is drafted for, and a guarded upsert that grades `replay_safe` and is only graded. A third, placeholder entry is there to replace with your own statement.
4. **Set the ledger permissions.** Before the job runs on a schedule, set who may write the ledger (table below, and "Security model"). Access to catalog objects on the platform is managed through Workbench roles, not SQL `GRANT` statements, which is why `sql/ddl_ops.sql` carries none: give the roles these permissions on the `nightshift_ops` schema and its tables.

   | Who | Needs | Why |
   |---|---|---|
   | the identity the job runs as (and the actuator's, if you use it) | owner of the schema, or every privilege on its tables | it creates the tables, inserts every row, and updates `approvals` itself: the claim, the outcome and the expiry sweep |
   | an approvers role | SELECT on the schema, UPDATE on `approvals` only | the Decide cell updates one row under the reviewer's own session |
   | everyone else | SELECT at most | INSERT or UPDATE on `approvals` or `policy_decisions` is the ability to forge or approve |

5. **Schedule the job.** Workflows, create a job with one Python task pointing at `/Workspace/Shared/nightshift/nightshift_heartbeat.py` on your cluster, cron `0 15/30 * * * ?` (every 30 minutes), timeout 1800 s, max concurrent runs 1. Set the environment variables you need (table below). The first run creates and drops its per-run sandbox schema, grades the watched statements and writes the tick.
6. **Review and approve.** Upload `notebooks/NightShift_Approvals.ipynb` to `Shared/nightshift/`. When an approval is pending, open it on the cluster, put the approval id in the first cell, run the Pending, Evidence and Draft cells, then run the Decide cell: it updates the row with `approved_by = current_user()`, your own identity. The next tick drains it and the last two cells show the runbook row and the executed approval. If you also run the external actuator, its approvals (`cluster_update`, `cluster_stop`, `job_disable`, `job_update_schedule`) appear in the same Pending table: check the `kind` column. Approving one of those lets the actuator's next `--apply` run change the cluster or the job, so the Decide cell refuses it unless you set `ALLOW_CONTROL_PLANE = True` in that cell.

## Environment variables

Read by the scheduled heartbeat unless marked otherwise.

| Variable | Default | Meaning |
|---|---|---|
| `NS_OPS` | `default.nightshift_ops` | the ledger schema (`<catalog>.<schema>`); the DDL in `sql/ddl_ops.sql` must be generated for the same name. The external actuator, the self-protection rule and every script in `scripts/` read this same variable (from `.env` on the laptop) |
| `NS_PKG` | `/Workspace/Shared/nightshift/pkg` | where the heartbeat imports the `nightshift` package from |
| `NS_SBX` | `default.nightshift_sbx` | sandbox base; each run uses `<base>_<tick>_<minute>` and drops it. A later run sweeps a schema left behind when its name is exactly that shape and its minute is between 3 h and 30 days back; no other schema sharing the base is touched |
| `NS_WATCHED` | `/Workspace/Shared/nightshift/watched_merges.json` | the watch list |
| `NS_DRAFT_ONLY` | unset | `1` skips the flight recorder and only grades, reuses verdicts and drafts (the external actuator's drafting pass) |
| `NS_JOB_NAME` | `nightshift_heartbeat` | runner name written as provenance on verdicts, drafts and decisions; also the drafting-lease owner and the scope of the one-hour backoff after a failed model call |
| `NS_DRAFT_MODEL` | `xai.grok-4.7` | `ai_generate` model id used for drafting in the `high` and `normal` tiers |
| `NS_DRAFT_MODEL_LOW` | `xai.grok-4.20-non-reasoning` | `ai_generate` model id used for drafting in the `low_compute` tier |
| `NS_DRAFT_ATTEMPTS` | `2` | model calls per statement per tick; with `NS_DRAFT_BEFORE_REPLAY=1` the run stops asking at the first reply the parser accepts |
| `NS_TASK_BUDGET_S` | `1800` | the run's time budget in seconds; set it to the job's timeout. No base replay starts with under 300 s left, and no draft is asked for, or replayed, unless its replay (timed from the statement's last one) fits after the replays already queued |
| `NS_REUSE_VERDICT_H` | `1` | hours; reuse a settled verdict that recent instead of replaying again. `NS_DRAFT_BEFORE_REPLAY` drafts from the reused verdict, so with `0` a run drafts right after its own replay |
| `NS_DRAFT_BEFORE_REPLAY` | `1` | make every model call of a run before its first replay: the drafts are asked for and validated first, then replayed; statements graded live are drafted next tick. `0` restores model call, replay, next model call |
| `NS_REPLAY_MAX_ROWS` | `2000000` | a watched table with more rows is reported as `skipped`, not replayed, and no draft is asked for or replayed for it (see "Things to know") |
| `NS_APPROVERS` | unset | comma-separated names allowed to lift a quarantine. For a statement repair, unset means any non-service identity. A control-plane approval (external actuator) is never executed while it is unset |
| `NS_FORCE_TICK` | unset | `1` ignores the idempotent half-hour window (measurement runs) |
| `NS_SHAPE_ALLOWLIST` | `amd.generic,VM.Standard.E4.Flex,VM.Standard.E5.Flex,VM.Standard3.Flex` | external actuator only: comma-separated worker shapes a resize action may choose from |

The heartbeat prints one JSON line per step (`replaying`, `replay_skipped`, `statement_graded`, `verdict_reused`, `drafting`, `drafting_skipped`, `drafting_deferred`, `draft_received`, `draft_failed`, `draft_rejected`, `draft_validated`, `draft_graded`, `draft_replay_skipped`, `draft_proof_failed`, `claim_release_failed`, `approval_opened`, `approval_skipped`, `approval_executed`, `approval_failed`, `approval_denied_on_execute`, `approval_drain_error`, `approval_drain_failed`) and a final summary, so the job's run output shows the tick as it happens.

## Validating

- Local: `python -m pytest` (528 tests, about a minute; pandas and duckdb stand in for Spark where syntax differs, and the tests say so). Three files go beyond unit checks: `tests/test_live_plan_duckdb.py` executes the generated live plan statement by statement in duckdb (staging, flags, every delivery and MERGE, diffs, coverage) for the shipped watch entries, known-bad statements and tables of 0 to 60 rows; `tests/test_heartbeat_offline.py` runs the scheduled job file itself end to end against a duckdb copy of the ledger, including the approval a person records and the next run draining it; `tests/test_actuator_ledger.py` runs the external tick across several ticks on real ledger rows. What no local test exercises is Spark's parser and Delta's MERGE: `watch.checked_watch` asks Spark for the parsed plan of each watched statement and each model reply, and the tests stub that call, so the first tick on your instance is the confirmation that the node allowlist matches your runtime (an unknown node rejects the statement; it never lets one through).
- Platform: after the first tick, `SELECT * FROM default.nightshift_ops.ticks ORDER BY started_at DESC` shows the tick, `replay_verdicts` the verdicts, `repair_drafts` the drafts and `approvals` what waits for a person. A run started by hand with Run now goes through the same path.

## Security model

Read this before scheduling the job. The code narrows what a mistake or a hostile row can do; the two controls below are yours to set and nothing in the code replaces them.

- **The workspace folder is code.** The scheduled job runs `nightshift_heartbeat.py` from the workspace folder and imports the `nightshift` package from `pkg/` beside it. Anyone who can write that folder (or the watch list in it) can run code as the job's identity. `Shared/` is writable by every workspace user by default: restrict write access on `Shared/nightshift/` to the job owner before the first run, or deploy to a folder only the owner can write and set the task path, `NS_PKG` and `NS_WATCHED` to match. The external actuator does not have this exposure: it sends the package and the heartbeat text inside the kernel cell it runs and never imports from the shared folder.
- **The ledger permissions are the approval control** (setup step 4). `approved_by` is a string in a table; it is as trustworthy as the permissions on that table. Only the identity the job runs as may INSERT into `<ops>.approvals` and `<ops>.policy_decisions`. UPDATE on `<ops>.approvals` belongs to that identity (its drain claims, marks and expires rows, which it can do as the owner of the schema) and to an approvers role, and to no one else. A principal that can insert into both tables can forge a quarantine and the approval that names it; the code cannot detect that, the permissions prevent it. Set `NS_APPROVERS` on the job (and in the actuator's environment). The notebook writes `current_user()` under the reviewer's own session, so the table's Delta history records who ran the update.
- **What the code enforces on top.** An approval only lifts a quarantine, and only the row the gate opened can do it. A row whose kind no quarantine rule holds (`cluster_stop`, a made-up kind) is marked `failed`. So is a row that names no quarantine decision of the gate for its action, which is every row written straight into `approvals`. A copy of a real approval names the real row's decision; the drain then finds two rows on one decision and executes neither, so a copy can block an approval but cannot stand in for one. The drain marks only the approved row it is looking at: a copy of an approval that is still pending is marked `failed` and the pending row is left for the reviewer, who then sees the reason on it when it is approved. What the code cannot tell apart is a principal that may UPDATE the real row: that is the approvers grant. A control-plane approval is never executed without `NS_APPROVERS`, and the names on that list must be what `current_user()` returns in your Workbench sessions. Unknown action kinds are denied by the gate. A model reply is untrusted text: one plain `MERGE`, parser-tree allowlist, declared target and source, replayed only inside the per-run sandbox schema. Applying an approved repair writes a runbook row and nothing else.
- **The flight recorder reads this cluster's own Spark UI with certificate verification off**, because the driver serves it under an address its certificate is not issued for. That client only reads stage and SQL metadata from the driver it runs on; do not reuse it for any other host.

## Things to know

- **What replay can grade.** One plain `MERGE` between two tables whose result is a function of the rows delivered, with no `DELETE` branch (the watched table holds no row such a branch would remove, so replay could not exercise it; the statement is recorded as `rejected`). A statement that fills a column from the clock (`merged_at = current_timestamp()`) differs from the recompute on every row and grades `snapshot_wrong`; watch the statement without that column or accept that it is not graded. Keys are taken as unique in the target (it is the result of a MERGE on them). The ordering column cannot be one of the keys, whether the keys come from the statement's `ON` equalities or from `key` in the watch entry: a statement such as `ON t.id = s.id AND t.updated_at = s.updated_at`, which keeps one row per version, is recorded as `rejected`, because a correction would be a new key and the revision check would pass without exercising anything. To grade it, declare the business key (`"key": ["id"]`) in the watch entry. A table with an array, map, struct or binary column grades `insufficient_coverage` and names the column (`revision:<column>` in `uncovered`): a correction cannot change such a value, so an `UPDATE` that forgets that column would not be caught.
- **What `replay_safe` does not cover.** Each delivery carries a key at most once: a source that can repeat a key inside one batch needs deduplication before the MERGE, and replay does not test for it (Delta inserts both rows of a new key, and raises when two source rows match one target row). A correction always moves the ordering value later and each other value to a different one, a NULL included (it becomes a fixed value of the column's type); the exception is an array, map, struct or binary value, which is left as it is and reported (see above). A row with no ordering value is never corrected, and a statement that orders by something other than the declared ordering column is not told apart from one that orders by it. No delivery repeats a key with an equal ordering value, so a guard written `>=` grades the same as one written `>`. The verdict is evidence about these delivery schedules on the table's current rows, not a proof for every input.
- **What replay costs.** Each graded statement clones the table (shallow), stages every row through one global sort, and applies the statement once per delivery: about 30 statement runs over the table's rows in total. That is minutes for a table of a few hundred thousand rows on a small cluster. `NS_REPLAY_MAX_ROWS` (default 2,000,000) is the guard: a larger table is reported as `skipped`. Raise it deliberately, on a cluster sized for it, or watch a representative smaller table.
- **Small tables.** A table with fewer rows than deliveries gets one row per delivery, and on a table under 40 rows each sampling flag also takes the first row, so its 1-in-10 modulus cannot miss everything. From two rows up every hazard has a row to act on. A table of one row, or an empty one, cannot exercise every hazard: it grades `insufficient_coverage`, and no draft is asked for it.
- **Identity of a scheduled run.** A scheduled run can present a different principal to the Generative AI service than the same job started by hand. If the model call is refused on the schedule but succeeds with Run now, grant that principal the Generative AI permissions in the lake's compartment; until then the job grades and gates on the schedule and drafts whenever a run is started by hand.
- **Long replays belong in job tasks**, not in notebook kernels: a replay of a large production statement can take 5 to 10 minutes, and a long kernel-side command can leave the cluster's command execution unhealthy.
- Pending approvals expire after 24 hours and the statement becomes draftable again. An approval left `executing` by a drainer that died is not retried; it expires an hour after the others would and a person decides again. A second run of the job inside an already recorded half-hour window ends at once.
- **The external actuator (optional, `scripts/run_tick.py`).** Dry run is the default: it shows what it would do, spends no rate quota and leaves an approved control-plane action for a run with `--apply`. Before it stops or resizes a cluster it asks the workspace for job runs in an active state (by status, so a page of run history cannot hide a long run) and treats a failed or unrecognised answer as "unknown", which denies. It sees job runs only: a notebook session someone has open on the cluster is not a job run, so do not point the actuator (`NS_CLUSTER_ID`) at a cluster people use interactively. Its drafting pass (`--draft`) runs the heartbeat in a kernel on the cluster, which has its own environment: the pass sends the ledger it used (`NS_OPS`) and, when they are set where the actuator runs, `NS_APPROVERS`, `NS_SBX`, `NS_DRAFT_MODEL` and `NS_DRAFT_MODEL_LOW`.
- The budget ledger holds estimates: `scripts/seed_budget.py` writes one shape-times-hours row per completed day (the Workbench API exposes no usage or cost data), and the scheduled job's tier follows it.

## Optional laptop tooling (`scripts/`)

These scripts drive the platform from outside the cluster through a workspace client: deploy the ledger and the workspace files, run the external actuator tick for control-plane actions (cluster stop or resize, dry-run by default), approve or reject from the command line, ingest failed runs and record incidents, seed the budget ledger, run the replay baseline on a statement from a file. They expect a class importable as `aidp_agent.AIDPClient`, which you supply: a signed client for the workspace REST API with the methods listed at the top of `nightshift/aidp_io.py` (jobs, job runs, clusters, metrics, notebook sessions and a generic signed request). `nightshift/aidp_io.py` imports it lazily, so nothing else in the sample needs it; the tests inject a fake. Laptop-side identifiers (region, data lake, workspace, cluster, OCI profile) come from a `.env` file next to the package; see `.env.example`. `scripts/stage_approvals_notebook.py --out file.ipynb` regenerates the approvals notebook locally.
