# V01: Amazon S3 through customer egress

Read a small private S3 object from AIDP through the customer's approved outbound path. Compare the same read before adding the S3 hostname, after adding it, and after restoring the original workspace settings.

## Prerequisites

Have an AWS account and an existing private bucket, bucket region, test object key, expected CSV rows and verified size up to 64 KiB. Keep S3 Block Public Access enabled. The supplied fixture contains `id,label`, then `1,alpha` and `2,beta`.

The compute administrator must provide compatible Hadoop S3A/AWS libraries and a supported credential provider on the driver and executors. Keep credentials in the approved secret mechanism. The notebook does not install libraries or create AWS resources.

Record the selected workspace/compute, customer subnet, current DNS/SCAN settings, S3 endpoint and actual bucket-specific hostname used by the client. An AWS VPC is not required for this public S3 endpoint design.

## IAM setup

AWS IAM authorizes the S3 read. An OCI dynamic group or IAM Network Source cannot grant S3 object access. Attach an identity policy like this to the AWS reader, replacing the bucket and object placeholders:

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {"Effect": "Allow", "Action": ["s3:GetBucketLocation", "s3:ListBucket"], "Resource": "arn:aws:s3:::<TEST_BUCKET>"},
    {"Effect": "Allow", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::<TEST_BUCKET>/<TEST_OBJECT_KEY>"}
  ]
}
```

The bucket-level grant accommodates the connector's metadata checks; object data access is limited to the test key. Cross-account access also needs an appropriate bucket policy. An SSE-KMS object additionally needs the relevant KMS decrypt authorization and key policy. Preserve any existing bucket source-IP restrictions; the approved OCI egress public IP must satisfy them. An Allow statement does not override an explicit Deny.

The OCI administrator separately verifies the existing AIDP private-network service permissions and Workbench workspace-edit access. These setup permissions are not the AWS runtime identity.

## Network setup

| Component | Required configuration |
| --- | --- |
| Workspace | Existing private connection to the selected customer VCN/subnet. |
| Customer route | IPv4 default route `0.0.0.0/0 -> NAT gateway`, or the approved equivalent outbound path. |
| Security | Stateful TCP 443 egress through applicable NSGs, security lists and firewalls; working DNS and return traffic. |
| Hostname | Actual regional and bucket-specific S3 FQDNs contacted by S3A. Use hostnames for TLS verification. |
| Workspace edit | Add only missing, service-resolvable client FQDNs under Advanced DNS. Keep existing entries and SCAN settings. |

Intended data path: AIDP -> workspace private connection -> customer subnet -> NAT/approved egress -> S3 public endpoint. A regional OCI service gateway is not an S3 route. Follow the existing platform network prerequisites; this table describes the additional destination path.

## Logging setup

Before testing, have the OCI administrator enable flow logs on the private connection's customer-side VNIC or subnet. Capture TCP source/destination port 443, accepted and rejected traffic, with 100% sampling for the test window. Record the actual VNIC and NAT public IP.

The AWS owner can enable S3 server access logging for the test bucket, using a separate authorized log destination, or use an approved CloudTrail configuration that records S3 object data events. Ordinary CloudTrail management-event history is insufficient for a GetObject trace. Agree logging retention and charges before enabling AWS collection.

Correlate UTC interval, bucket/key, GetObject, request ID, AWS reader and the source address seen by S3 with the customer-side flow and egress configuration. S3's apparent client address can be a NAT/proxy address. Log delivery can be delayed or incomplete; an empty search does not establish that traffic was absent. Disable test-only collection after validation.

### Enable collection before the test

1. Have an administrator create/reuse an approved regional log group. Example logging-operator policies -- replace the domain, group and compartments:

   ```text
   Allow group <IAM_DOMAIN>/<LOG_OPERATORS> to manage log-groups in compartment <LOG_COMPARTMENT>
   Allow group <IAM_DOMAIN>/<LOG_READERS> to read log-content in compartment <LOG_COMPARTMENT>
   Allow group <IAM_DOMAIN>/<LOG_OPERATORS> to {SUBNET_READ, SUBNET_UPDATE} in compartment <NETWORK_COMPARTMENT>
   ```

2. In **Networking > Network Command Center > Flow logs**, select the customer private-connection subnet/VNIC and log group. Use a dedicated flow-log capture filter with TCP source OR destination port 443, INCLUDE both accepted/rejected traffic, and 100% sampling. The network administrator supplies the filter; do not edit a shared filter. Confirm the log is enabled and ACTIVE.
3. The AWS bucket owner enables **S3 Properties > Server access logging** to a separate approved bucket in the same account/region, or configures CloudTrail **S3 object data events** for the test bucket. Ordinary CloudTrail event history is insufficient for GetObject. Use the linked AWS setup instructions for log delivery permissions. Allow delivery time and capture a fresh GET.
4. In **Logging > Search**, select the correct region, log and UTC interval. Match VNIC, source/destination addresses and ports, protocol, action and capture status. Empty results can reflect delay, capture loss or the wrong VNIC; ACCEPT alone does not establish application authorization. Never copy credential fields into an evidence export.

If setup returns `NotAuthorizedOrNotFound`, verify operator permissions in both resource and log compartments, plus source endorsement/destination admission for cross-tenancy administration. Do not expand the test reader's permissions to solve a logging-operator error. Review retention and logging costs with the resource owner; disable only test-created collection after validation.

See [Logging permissions](https://docs.oracle.com/en-us/iaas/Content/Logging/Task/managinglogs.htm) and [flow-log setup](https://docs.oracle.com/en-us/iaas/Content/Network/Tasks/vcn-flow-logs-enable.htm).

## Customer steps

1. Complete AWS authorization, connector, network and logging prerequisites. Save the complete workspace DNS/SCAN baseline.
2. Attach the intended compute. Run **Initialize V01**, fill **Your configuration**, then run that configuration cell once. Leave credentials out of the dictionaries.
3. Set `RUN_LIVE=True` and `PHASE="before"` under **Choose phase**. Run the driver diagnostic and the S3 read. Record the real result; an already successful baseline is valid.
4. Add only the missing S3 client hostname entries. Save, inspect the update result, reopen the workspace and verify the final configuration. Follow any required compute lifecycle action; do not assume changes propagate to every running compute.
5. Use a fresh client/session as needed for caching. Set `PHASE="after_add"`; repeat the same object read with unchanged AWS identity and endpoint. Correlate its UTC interval with both sides' logs.
6. Restore only entries introduced by this test. Set `PHASE="restored"`, repeat and export. Preserve earlier results before any session restart, then initialize and configure the new session.

## Configuration

Use `uri="s3a://<bucket>/<key>"`, `endpoint="s3.<aws-region>.amazonaws.com"`, and the bucket's `region`. Set `hostname` to the actual client FQDN being investigated, including its bucket prefix when applicable; port is 443. Record known `fixture_size_bytes` and exact `expected_rows`. Workspace/compute labels describe the selected environment; they do not attach compute.

## Expected results

`READ_PASSED` means the exact fixture rows were read with authentication. `SETUP_REQUIRED` identifies a prerequisite; `FAIL` identifies an executed check failure. `source_path: NOT_ASSESSED` asks for the matching flow/S3 evidence and does not mean the read failed.

Accept the customer-egress claim after reviewing the flow, NAT/egress mapping and matching S3 event. A `255.x.x.x` DNS answer is a translated destination, not the customer's source address. Before/restored results should be consistent with the original configuration; neither must be forced to fail.

## Troubleshooting

| Symptom | Next check |
| --- | --- |
| S3A class missing / NoSuchMethodError | Match Hadoop, S3A and AWS libraries on driver and executors. |
| Wrong-region redirect / signature-region error | Bucket region, regional endpoint, bucket hostname and credential-provider configuration. |
| DNS error / Python and JVM disagree | Exact client FQDN, cached answers and completed workspace update. Driver probes do not cover executors. |
| TCP timeout | Customer egress route, NAT, security rules and matching VNIC flow records. |
| AccessDenied | AWS identity policy, bucket policy, explicit Deny, source-IP condition and KMS policy. |
| Read succeeds but route is uncertain | Correlate the fresh request with S3 and customer-VNIC evidence. |

For Oracle Support, provide workspace/compute identifiers, client FQDN, UTC update and test intervals, workspace update request ID, and sanitized network/request evidence. Support can correlate the workspace's network configuration and child update workflow. A workflow launch does not prove data-plane routing.

## Restore and export

Restore the original DNS/SCAN configuration and repeat the final phase. Disable test-only logging and stop compute only if this test started it. Export results and references privately. Preserve shared buckets, routes and policies. No AWS account or bucket is created by this notebook.
